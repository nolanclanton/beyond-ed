# ADR 0007 — Beyond.Ed is standalone software; the organization is a tenant

**Status:** Accepted
**Date:** 2026-08-22

## Context

The project began as a platform built for one named school network, and that
name had leaked into places it did not belong: the application shell, page
metadata, the landing page, the design tokens, the seed data, the README, and
the governing document itself.

The owner asked for every formal reference to be removed so the product reads as
freestanding software, while keeping the structure and synthetic data as they
are.

That is not only a naming change. A customer name hardcoded into a component is
a design defect in multi-tenant software: it means the product cannot serve a
second organization without editing markup.

## Decisions

### 1. The organization is a record, not a literal

`AppShell` reads the tenant from the `organizations` table using the signed-in
user's `orgId`, and renders nothing where the record is absent. No component
under `/app` or `/lib/design` names an organization. The database already
modelled this correctly — the interface simply was not using it.

### 2. One file defines the demo tenant

`lib/db/demo-identity.ts` holds the demo organization and its five sites, with
the per-site staffing and enrollment counts. The seeder imports it and nothing
else names a site. Rebranding the demo is a single edit; serving a real district
is a different seed, not a different build.

Site identifiers changed along with the names so nothing in the codebase carries
a residual reference to the previous ones.

### 3. The demo tenant is obviously fictional

**Northfield Learning Network**, with sites Northfield Central, Riverside,
Oakmont, Lakeview, and Summit. Generic placenames, chosen so no real school,
district, or network is implied. The landing page says in the beta banner that
the tenant is fictional and that the organization is a record the product reads
rather than something built into it.

The synthetic population is unchanged: the same 584 students, 37 teachers, and
per-site counts, generated by the same deterministic seed.

### 4. The brand colour stays; its name does not

`#481514` remains the product's brand maroon. It was previously described in
`lib/design/tokens.ts` and in CLAUDE.md §13 as a specific organization's colour;
it is now simply the product's, and its role is unchanged — branding only, never
a status or an action colour.

### 5. CLAUDE.md was amended, at the owner's request

Three lines tied the product to a specific customer: the opening product
description, the source-control row in the approved stack table (§1), and the
palette rule (§13). Editing the governing document is not something to do
quietly, so the shape of the change is recorded here:

| Line | Was | Now |
|---|---|---|
| Product description | Named a specific school network as the customer | "a **standalone** grades 6–12 platform … the organization it serves is a tenant record" |
| §1, source control | Attributed repository ownership to that network | "**Owner-controlled** GitHub / All history stays owned by the repository owner" |
| §13, palette | Described `#481514` as that network's colour | "**Brand maroon** anchors product branding" |

No invariant changed. Nothing in §0's nine invariants concerns who the customer
is, and none of them were touched.

## Consequences

- The product can serve a second organization without a code change.
- A reviewer sees Beyond.Ed as software, with a demo district plainly labelled
  as demo data.
- The blueprint in `docs/blueprint.md` needed no edit: it never named the
  organization, only the product.
